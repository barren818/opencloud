## 阶段一 · 用户与权限管理

**一句话**：一家公司里谁能进哪个目录、能读还是能写，先把人和规矩建好，后面所有阶段都站在它上面。

**做了什么**
- 3 个组：`developers` / `webadmins` / `auditors`；6 个用户：`dev01` `dev02` / `web01` `web02` / `audit01` `audit02`。
- `/company` 目录树：`development/project_A`、`project_B`，`website/html`、`website/logs`，`reports`、`backup`。
- 权限做法：属组给读写的那组，`chmod 2770`（`2` 是 setgid，新文件继承属组；`770` = 属主、属组可读写执行，其他人什么都没有），再用 `setfacl` 给只读的那组补 `r-x`。
- 7 项验证：用 `su - 用户名 -c '...'` 换身份测，**其中“失败”的是预期结果**——`audit01` 写 `project_A`、`audit01` 写 `backup`、`dev01` 改 `index.html` 本来就该报 `Permission denied`，别当成出错去修。

**三个要记住的点**
1. 概念：基础权限（`rwx` 属主/属组/其他人）只能指定**一个**属组；要让第二组人只读，就得加 ACL（`setfacl`），不是把目录放开给所有人。
2. 排查路径：权限问题先 `ls -ld` 看基础权限，再 `getfacl` 看 ACL 和 `mask`——`mask` 会把组权限压下来（阶段五 `index.html` 就栽过一次：组和 mask 都是 `r--`，`webadmins` 实际只能读）。
3. 东西在哪：用户和组是系统状态，不是文件，阶段十二靠部署文档记录；目录在 `/company` 下。

**复现（只读）**
```
getent group developers
getent group webadmins
id web01
ls -ld /company/website/html
getfacl /company/website/html
```
预期：每组两个人；`html` 目录属组 `webadmins`，`getfacl` 里有 `group:developers:r-x`、`group:nginx:r-x`、`mask:rwx`、`other::---`。

## 阶段二 · 磁盘分区与 LVM

**一句话**：加一块 20GB 实验盘，把它切成三块能伸缩的逻辑卷，分别装项目、网站、备份数据。

**做了什么**
- PV → VG `company_vg` → 三个 LV：`project_lv`、`website_lv` 8G、`backup_lv` 4G，ext4，分别挂在 `/company-data`、`/website-data`、`/backup-data`，写进 `/etc/fstab` 开机自动挂载。
- `project_lv` 扩过两次：5G → 6G（阶段二原计划），6G → 7G（阶段六场景 04 救火时扩的），每次都是 `lvextend` + `resize2fs` 在线扩，不用停机。
- 现状注意：扩完之后 `company_vg` 空闲已不足 1G，以后再想扩卷基本没余地了。

**三个要记住的点**
1. 概念：LVM 三层是 PV（物理盘）→ VG（池子）→ LV（从池子里切出来的卷）；扩容是先扩 LV 再扩文件系统，两步缺一不可。
2. 排查路径：空间问题先 `df -h` 看哪个卷满，再 `vgs` 看池子还有多少空闲、能扩多少，最后 `du -sh 目录/*` 定位是谁占的。
3. 东西在哪：卷名用 `lvs` 看，挂载用 `df -h` 看，开机挂载的规矩在 `/etc/fstab` 里。

**复现（只读）**
```
lvs
df -h
cat /etc/fstab
```
预期：`company_vg` 下 `project_lv` 7G、`website_lv` 8G、`backup_lv` 4G；`df` 里三行挂载点都在，使用率都是个位数；`fstab` 里三行都没有行首 `#`。

## 阶段五 · Nginx 企业内部网站（你问得最多的那段）

**一句话**：把 Nginx 装起来，网站根目录改到 `/company/website/html`，让宿主机浏览器能打开首页，并且按组管好谁能改网页、日志写到指定目录。

**做了什么**
- Nginx 1.21.5，装好并开机自启；首页 `index.html` 544 字节，放在 `/company/website/html`（注意：**不是**方案原写的 `/website-data/html`，因为当时阶段二还没做）。
- 根目录改完后本机 `curl` 报 **403**：根源是新目录的 SELinux 标签还是 `default_t`，Nginx 没权限读。**没有关 SELinux**，正规修法是 `semanage fcontext -a -t httpd_sys_content_t '/company/website/html(/.*)?'` + `restorecon -Rv` 打标签。
- 防火墙放行：`firewall-cmd --permanent --add-service=http` + `--reload`；宿主机 PowerShell 测 `192.168.6.135:80` 通；Windows 浏览器打开 `http://192.168.6.135`，`access.log` 记下 `192.168.6.1 GET / 200`（Edge，544 字节）。
- 日志改道：`nginx.conf` 里 `access_log` / `error_log` 指向 `/company/website/logs`，该目录标签打成 `httpd_log_t`；`error.log` 的文件名曾笔误写成 `erroe.logs`，已改回。
- 权限收尾（任务 4）：`html` 目录 ACL 验收满分（属主 `web01`、属组 `webadmins`、setgid 在、`developers` 只读、`nginx` 只读、其他人无权）；`index.html` 的组和 `mask` 曾被压成 `r--`，用 `setfacl -m g::rw-` 和 `setfacl -m m::rw-` 修回 `rw-`。
- 日志核对：故意访问 `/nope.html` 得 404，`error.log` 有对应报错；`favicon.ico` 的 404 无害。

**三个要记住的点**
1. 概念：403 不一定是权限数字错了——普通权限都对时，要去看 SELinux 标签（`ls -Z`）；标签不对，`chmod 777` 也救不了，还更糟。
2. 排查路径：403 → 先 `ls -l` / `namei -l` 查普通权限 → 再 `ls -Z` 看标签 → `getenforce` 确认是不是 Enforcing 在拦。
3. 东西在哪：网站根目录 `/company/website/html`；配置 `/etc/nginx/nginx.conf`；日志 `/company/website/logs/`；改配置前先 `nginx -t` 自检，再 `reload`。

**复现（只读，5 分钟）**
```
curl -I http://127.0.0.1
ls -Z /company/website/html
getfacl /company/website/html
nginx -t
```
预期：`200 OK`；目录标签 `httpd_sys_content_t`；`getfacl` 与阶段一那节一致；`nginx -t` 显示 `syntax is ok`、`test is successful`。

## 阶段七 · Shell 自动化运维

**一句话**：把“每天看一眼磁盘、每 5 分钟看一眼 Nginx”这两件重复活写成脚本，交给 cron 自动跑。

**做了什么**

## 阶段八 · 备份与恢复

**一句话**：网站和项目每天有包可回滚，改坏了、删错了能从包里把单个文件捞回来。

**做了什么**
- 目录：`/backup-data/{daily,weekly,restore_test}`。
- tar 打包：网站包 `website-2026-11-17.tar.gz`（530B，清单干净，只含 `html/index.html`）；项目按 A、B 分开打过两包——两包同名互相覆盖过一次，是你自己从 `ls` 里发现并改名修好的。
- rsync 增量同步：`rsync -av /company/website/html/ /backup-data/website_sync/`。第一遍全量；改了两个文件后第二遍只传了那两个（787 字节）；没改动时第三遍清单为空（127 字节开销）——增量机制实证。
- 误删恢复演练（全闭环）：`test_restore.html` 打进当日网站包并验清单 → 删原件 → 从包里单独解出到 `restore_test` 验内容 → 拷回网站目录 → `curl` 返回原文。
- 备份 cron（root crontab 现共 4 行：阶段七 2 行 + `0 22 * * *` 网站日备 + `0 23 * * 0` Nginx 配置周备；`date` 里的 `%` 都写成了 `\%F` 转义，否则 cron 会截断命令）。

**tar 再讲一遍（你收官后要求重讲的，骨架先行）**
```
tar -czf 包名.tar.gz -C 目录 要打的文件
tar -tzf 包名.tar.gz
tar -xzf 包名.tar.gz -C 目标目录
```
- 动作字母只取一个：`c` = 打包（create），`t` = 列清单（list，只看不解），`x` = 解包（extract）。
- `z` = 顺手 gzip 压一下（包名才有 `.gz`）；`f` = 后面跟的那个就是包文件名（`f` 后面必须紧跟包名）。
- `-C 目录` = 先 `cd` 进那个目录再打包/解包——它决定包里路径长什么样。忘了 `-C`、直接打绝对路径，包里就会带上整条 `/company/...`，解出来也按那条路放，容易解错地方。
- 对照你做过的：`tar -czf website-2026-11-17.tar.gz -C /company/website html` 是“进到 `/company/website` 里，只打 `html`”；`tar -tzf` 是验包（打包后必做的一步）；恢复时 `tar -xzf 包 -C /backup-data/restore_test` 是“解到指定地方验内容，别直接盖回原处”。

**rsync 一句话**：它先比对两边的文件（改没改、大小/时间变没变），只传变了的部分；`tar` 是“整包拍一张快照”，`rsync` 是“只同步差异”——两个工具分工不同，不是二选一。

**三个要记住的点**
1. 概念：备份分两层——`tar` 打带日期的整包（能回滚到某一天），`rsync` 做增量同步（每天只传变化，省时间省空间）。
2. 排查路径：恢复时先 `tar -tzf` 看包里到底有什么，确认有要的文件再解；解到 `restore_test` 验内容，验对了再拷回原处，别直接往原目录解。
3. 东西在哪：包在 `/backup-data/daily/`（网站日备）和 `/backup-data/weekly/`（Nginx 配置周备）；同步目录 `/backup-data/website_sync/`。

**复现（只读）**
```
ls -l /backup-data/daily/
ls -l /backup-data/weekly/
tar -tzf /backup-data/daily/website-2026-11-17.tar.gz
ls /backup-data/website_sync/
```
