# 故障排查手册

**项目**：openEuler 企业服务器综合部署与运维实战（单机云计算综合实验）
**环境**：Windows 11 + VMware，openEuler 22.03 LTS SP4，Nginx 1.21.5
**说明**：本手册汇总阶段六综合故障排查的全部案例，同时收录实验过程中真实发生的故障。每个案例按「现象 → 排查 → 原因 → 修复 → 验证」记录，作为阶段十二交付物之一。

---

## 案例 01：Nginx 服务停止，网站无法访问

- **故障现象**：公司内部网站打不开。在虚拟机本机执行 `curl -I http://127.0.0.1`，返回 `curl: (7) Failed to connect to 127.0.0.1 port 80: Connection refused`。
- **排查过程**：
  1. 先在本机测回环地址 127.0.0.1，结果为 Connection refused。本机测试不经过网络，说明主机与网络层正常，但 80 端口上没有任何程序监听，问题锁定在服务本身。（经验：refused 表示主机可达但端口无监听；timeout 则多为网络路径不通或防火墙丢弃报文，两者指向完全不同的排查方向。）
  2. 执行 `systemctl status nginx`，显示 Active: inactive (dead)，服务确实已停止。
  3. 执行 `ss -lntp | grep :80`，无任何输出，确认 80 端口无进程监听，与服务状态互相印证。
- **原因**：Nginx 服务被停止（本案例为人为停服模拟），进程不存在，80 端口无人监听。
- **修复方法**：执行 `systemctl start nginx` 重新启动服务。
- **验证结果**：服务恢复 active (running)；`curl -I http://127.0.0.1` 返回 HTTP/1.1 200 OK；Windows 浏览器可正常打开网站首页，故障排除。

## 案例 02：网站文件权限错误（SELinux 标签）导致 Nginx 403

> 本案例为阶段五部署过程中真实发生的故障，非模拟。

- **故障现象**：将 Nginx 网站根目录由默认的 /usr/share/nginx/html 改为 /company/website/html 并重载服务后，本机 `curl http://127.0.0.1` 返回 **403 Forbidden**（此前使用默认根目录时访问正常）。
- **排查过程**：
  1. 检查普通权限：`ls -l` 显示 index.html 为 -rw-r--r--，文件本身可读；`namei -l /company/website/html/index.html` 显示路径各级目录均有 x 权限，普通权限没有问题。
  2. `ps` 确认 Nginx 工作进程运行用户为 nginx；`getenforce` 返回 Enforcing，将怀疑转向 SELinux。
  3. `ls -Z` 查看网站目录，SELinux 标签为 `default_t`；执行 `ausearch -m AVC -ts recent` 抓到审计记录 `avc: denied { getattr } comm="nginx" ... tcontext=...:default_t`，证实是 SELinux 策略拦截（Nginx 进程域 httpd_t 无权访问 default_t 类型的内容）。
- **原因**：网站目录建在 /company 下，其 SELinux 文件上下文为 default_t，与 Web 服务要求的 httpd_sys_content_t 不匹配，Enforcing 模式下被拒绝访问。
- **修复方法**：不关闭 SELinux、不用 chmod 777，采用正规打标签方式：
  1. semanage 命令缺失，先安装提供它的软件包：`dnf install -y policycoreutils-python-utils`。
  2. 添加文件上下文规则：`semanage fcontext -a -t httpd_sys_content_t '/company/website/html(/.*)?'`（/company、/company/website 两级目录同样处理）。
  3. 应用标签：`restorecon -Rv /company/website/html`。
- **验证结果**：`ls -Zd` 显示目录标签已变为 httpd_sys_content_t；`nginx -t` 通过；`curl -I http://127.0.0.1` 返回 HTTP/1.1 200 OK，Windows 浏览器访问正常，故障排除。

## 案例 03：DNS 解析失败，域名无法访问

- **故障现象**：服务器"上不了网"，执行 `ping www.baidu.com` 报错 `Name or service not known`，域名解析失败。
- **排查过程**：
  1. ping 域名在解析阶段即失败，尚未走到网络连接，先怀疑解析层。
  2. 尝试 ping 公共 DNS 地址 114.114.114.114，结果 100% 丢包。此结果不可靠：公共 DNS 服务器通常不回应 ICMP echo，不能据此判定网络不通。（教训：测 IP 层连通性应选网关等确定会回应 ICMP 的地址，不要拿公共 DNS 服务器当 ping 目标。）
  3. 执行 `cat /etc/resolv.conf`，发现 nameserver 只剩下无效地址 192.0.2.1，原有的 114.114.114.114 与 192.168.6.2 均已不在，原因定位在 DNS 配置。
- **原因**：/etc/resolv.conf 被改写，DNS 服务器指向不存在的 192.0.2.1，无任何可用解析服务器（本案例为人为改坏配置模拟）。
- **修复方法**：用修改前备份的文件还原：`cp /etc/resolv.conf.bak /etc/resolv.conf`，恢复为 114.114.114.114（主）+ 192.168.6.2（备）双 nameserver 配置。
- **验证结果**：`ping -c 2 www.baidu.com` 成功解析出 IP 39.156.70.239，收到 2/2 回复、0% 丢包，域名解析与网络访问同时恢复正常。

## 案例 04：逻辑卷空间不足（/company-data 达 96%）

- **故障现象**：`df -h` 显示 /company-data（project_lv）使用率 96%，仅剩 241M 可用，其余文件系统均正常。（本案例以 dd 写入 5.3G 测试文件模拟业务数据暴涨。）
- **排查过程**：
  1. `df -h` 对比各文件系统，确认只有 /company-data 一个卷异常，问题范围锁定。
  2. `vgs` 查看卷组：company_vg 尚有不足 2G 的空闲空间，确认存在扩容余地（同时决定了扩容幅度上限）。
  3. `du -sh /company-data/*` 逐项排查，定位到单个文件 bigfile.img 独占 5.3G，其余文件合计可忽略。
- **原因**：单个异常大文件占满逻辑卷空间，导致该卷可用空间耗尽。
- **修复方法**：按"先扩容保可用、再清理"的顺序处置：
  1. 扩容：`lvextend -L +1G /dev/company_vg/project_lv`（6 GiB → 7 GiB；VG 空闲不足 2G，只扩 1G 留有余量），再 `resize2fs /dev/company_vg/project_lv` 在线扩大 ext4 文件系统（挂载状态下完成，无需停机）。使用率由 96% 降至 82%，可用空间由 241M 回升至 1.2G。
  2. 清理：确认 bigfile.img 为测试垃圾文件后删除：`rm /company-data/bigfile.img`。
- **验证结果**：`df -h` 显示 /company-data 使用率回落至约 1%，空间完全恢复；project_lv 保持扩容后的 7G。

## 案例 05：配置错误导致 Nginx 服务启动失败

- **故障现象**：修改配置后执行 `systemctl restart nginx`，返回 `Job for nginx.service failed because the control process exited with error code`，Nginx 未能启动，网站下线。
- **排查过程**：
  1. 执行 `systemctl status nginx`，显示 `Active: failed (Result: exit-code)`，确认服务启动失败。
  2. status 中 Process 行显示启动前自检命令 `ExecStartPre=/usr/sbin/nginx -t` 以 status=1/FAILURE 退出，说明服务是在配置自检阶段被拦下，根本没有进入启动。
  3. status 附带的日志记录给出确切原因：`nginx: [emerg] unknown directive "badconfig" in /etc/nginx/conf.d/broken.conf:1`，以及 `configuration file /etc/nginx/nginx.conf test failed`。（同类问题也可通过 `journalctl -u nginx` 查看完整日志，定位方法一致。）
- **原因**：conf.d 目录中存在一个包含非法指令 `badconfig` 的配置文件 broken.conf，Nginx 加载全部配置时自检失败，拒绝启动（本案例为人为放入坏配置模拟）。
- **修复方法**：删除坏配置文件 `rm -f /etc/nginx/conf.d/broken.conf`，执行 `nginx -t` 复检通过后 `systemctl start nginx` 重新启动。
- **验证结果**：`nginx -t` 显示 syntax is ok、test is successful；服务正常启动；`curl -I http://127.0.0.1` 返回 HTTP/1.1 200 OK，网站恢复访问。
- **经验**：修改任何 Nginx 配置后、重启服务前，先执行 `nginx -t` 自检，可避免把配置错误直接带成停机事故。

## 案例 06：fstab 条目被注释，重启后文件系统未自动挂载

- **故障现象**：重启服务器后，`df -h` 中 /website-data 整行消失，`ls /website-data` 显示为空目录，看似"数据盘丢失"；系统本身正常启动，其余数据卷挂载正常。
- **排查过程**：
  1. `df -h` 对比各文件系统：仅 /website-data 未挂载，/company-data、/backup-data 均正常，问题锁定在单个卷的挂载环节。
  2. `lvs` 确认 website_lv 完好存在（8G），卷与数据并未丢失，只是没有被挂载上来；挂载点目录本身只是根文件系统上的一个空目录，未挂载时自然为空。
  3. `cat /etc/fstab` 检查自动挂载配置：/website-data 一行的行首被加上了 `#`，整行成为注释，开机时被跳过。
- **原因**：/etc/fstab 中 /website-data 的条目被注释，重启后 systemd 没有为其生成挂载单元，未执行自动挂载（本案例为人为注释条目模拟）。
- **修复方法**：
  1. `vi /etc/fstab` 删除该行行首的 `#`，恢复条目生效。
  2. `systemctl daemon-reload`，让 systemd 按新 fstab 重新生成挂载单元（fstab 文件开头注释亦有此要求）。
  3. `mount -a` 按 fstab 立即挂载全部文件系统，/website-data 当场恢复，无需等重启。
- **验证结果**：再次重启服务器，`df -h` 显示 website_lv 已自动挂载于 /website-data（7.8G，使用率 1%），其余卷亦全部正常，自动挂载功能确认恢复。
- **经验**：遇到"目录突然变空"，先查挂载（df/mount）再查数据，多数情况是未挂载而非数据丢失；修改 fstab 后应执行 daemon-reload，并以 mount -a 或重启验证。

## 案例 07：容器端口映射僵死，外部无法访问已发布端口

- **故障现象**：Podman 容器 nginx-web 运行正常，宿主机 `curl http://127.0.0.1:8080` 可返回网站首页；但 Windows 浏览器访问 http://192.168.6.135:8080 时页面长期无响应，宿主机以自身对外 IP `curl http://192.168.6.135:8080` 同样挂起。
- **排查过程**：
  1. `podman ps` 确认容器状态 Up、端口映射 `0.0.0.0:8080->80/tcp` 存在；`firewall-cmd --list-ports` 确认 8080/tcp 已永久放行。
  2. 临时 `systemctl stop firewalld` 后复测，故障依旧，排除防火墙拦截；`sysctl net.ipv4.ip_forward` 确认为 1，排除 IP 转发开关未开。
  3. `curl -v` 显示 TCP 握手完成（Connected）、GET 请求已发出，但始终无响应返回；`podman logs nginx-web` 中无任何外部访问记录（最后一条仍为本机测试的 200），判定请求根本未送达容器。
  4. `ss -tlnp | grep 8080` 发现 8080 由 conmon 进程监听（Podman 的端口发布由 conmon 托管监听并向容器转交）；`curl http://10.88.0.2:80` 直连容器 IP 秒出首页，证明容器本体与容器网桥均正常，故障锁定在端口发布层。
- **原因**：容器首次启动时建立的端口发布状态僵死：发布端口可完成 TCP 握手，但连接未被继续转交至容器，请求无法到达容器内服务（发布层内部细节未进一步下钻，以重建发布状态处置）。
- **修复方法**：
  1. `podman stop nginx-web` 停止容器，`podman rm nginx-web` 删除容器（网站数据位于宿主机挂载目录 /opt/webhtml，删除容器不影响数据）。
  2. 以原始 `podman run` 命令（相同镜像、-p 8080:80 端口映射、-v 挂载与 :ro,Z 参数）重建容器，端口发布状态随容器创建整套重建。
  3. 附带将 `net.ipv4.ip_forward = 1` 写入 /etc/sysctl.d/99-ip-forward.conf 持久化，保证转发开关每次开机生效。
- **验证结果**：`curl http://192.168.6.135:8080` 秒出首页；Windows 浏览器打开 http://192.168.6.135:8080 正常渲染企业网站首页；`podman stop` / `podman start` 生命周期复测后访问依旧正常。
- **经验**：按层排除（防火墙 → 转发开关 → 服务日志 → 端口监听者 → 直连服务本体）能快速把故障收敛到具体一层；容器类故障不必逐行修复内部状态，数据在挂载卷中时，按原参数重建容器是标准且高效的处置方式。
