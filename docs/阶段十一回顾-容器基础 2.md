# 阶段十一回顾 · 容器基础（Podman）

**用途**：上午的操作是"救火节奏"跑完的，这份文档把当时来不及讲的概念补齐，把你亲历的每件事翻译成知识。看的时候不用背命令，重点看"为什么"。
**环境事实**：Podman 3.4.4（openEuler 官方源安装）；镜像 nginx:latest（167 MB，镜像内 nginx 版本 1.31.9）；容器名 nginx-web；宿主机对外地址 192.168.6.135，容器地址 10.88.0.2。

---

## 一、一句话总览

阶段十一做了一件事：**在已经跑着一个 Nginx 网站的服务器上，再用容器的方式跑第二个 Nginx**，两个网站同机共存、互不干扰（80 端口 = 宿主机版 1.21.5，8080 端口 = 容器版 1.31.9），并完整练了一遍容器的生老病死：拉镜像、起容器、看日志、进容器、停、启、删、重建。

## 二、概念地基（上午缺的那堂课）

### 1. 容器和虚拟机到底差在哪

你最熟的是虚拟机：VMware 里这台 openEuler 是一台完整的"电脑" — 有自己的内核、自己的内存和硬盘，开机要走一分钟的启动流程，体积以 GB 计。

容器是在**一台已经跑着的 Linux 里面**，用内核的隔离功能（namespace + cgroup）隔出一个小间：里面的进程以为自己独占一台机器，其实**借用的是宿主机的内核**。所以：

| | 虚拟机 | 容器 |
|---|---|---|
| 自带内核 | 有，每台一份 | 没有，共享宿主机的 |
| 启动 | 分钟级（走完整开机） | 秒级（本质是起一个进程） |
| 体积 | 几个 GB 起 | 本例镜像 167 MB |
| 隔离强度 | 强（硬件级虚拟化） | 弱一些（同内核） |
| 典型用途 | 跑不同的操作系统、强隔离 | 快速部署/复制同一个服务 |

一句话：**虚拟机虚拟的是一台电脑，容器虚拟的是一个进程的运行环境。**

### 2. 镜像 / 容器 / 仓库

- **镜像（image）**：只读的打包模板，里面装着程序和它需要的完整环境。类比 VMware 的虚拟机模板，或一台电脑的"系统备份盘"。镜像是**分层**的 — 你拉取时看到的 7 个 `Copying blob ... done` 就是 7 层，像千层饼一样叠成一个完整系统。
- **容器（container）**：镜像跑起来的活实例。同一个镜像可以起很多个容器；容器可以停、删、重建，镜像纹丝不动。你上午亲手验证过：nginx-web 被 stop/rm 了两轮，镜像一直在，`podman images` 里躺得好好的。
- **仓库（registry）**：存放镜像的网上仓库，`pull` = 下载，`push` = 上传。镜像全名拆开是 `仓库地址/命名空间/镜像名:版本标签`，如 `docker.io/library/nginx:latest`；平时简写 `nginx` 指的就是它。
- **tag**：给镜像起的别名。你上午把 `docker.m.daocloud.io/library/nginx:latest` tag 成 `nginx:latest` 后，`podman images` 里两行是**同一个 IMAGE ID** — 一个东西、两个名字，磁盘上只存一份。

### 3. 端口映射：外面的人怎么找到容器

容器有自己独立的网络，住在内网小区里（本例网段 10.88.0.0/16，网桥叫 cni-podman0，相当于小区的交换机；容器的门牌号是 10.88.0.2，网关 10.88.0.1 是宿主机）。

外面（你的 Windows）不知道小区在哪，所以要在宿主机大门上挂个牌子：**`-p 8080:80` = 宿主机的 8080 端口收到的连接，全部转交给容器的 80 端口**。这和 VMware 的 NAT 端口转发是同一个思想，你早就理解了，只是换了个执行者。

为什么不用 80 而用 8080？因为宿主机的 80 已经被阶段五的 Nginx 占了 — 容器内部照常用标准端口，对外靠映射错开，这正是容器部署的日常手法。

还有一个角色要认识：**conmon**。它是 Podman 派给每个容器的"监工进程"，负责看管容器、收集日志（`podman logs` 看的就是它存的）、并托管发布端口的监听 — 你上午在 `ss` 里看到 8080 的监听者是 conmon，就是它。

### 4. 挂载：文件在外面，容器只是借用

`-v /opt/webhtml:/usr/share/nginx/html:ro,Z` 的意思是：把宿主机的 `/opt/webhtml` 目录，塞进容器里当它的网站根目录用。

- 这和 VMware 共享文件夹是一个道理：**文件本体在宿主机上，容器只是借看**。推论非常重要：容器删了，文件还在；改宿主机上的文件，容器立刻看到（不需要重启容器 — 上午 chmod 之后直接 curl 就生效，你验证过）。
- `ro` = 只读，容器里的程序改不动这份文件，安全。
- `Z` = 给这份文件打上容器能读的 SELinux 标签（见下一节）。
- 为什么挂的是副本目录 /opt/webhtml，而不是网站原目录 /company/website/html？因为原目录的 SELinux 标签和权限是给宿主机 Nginx 量身定的，硬挂给容器会水土不服（阶段五的教训）。给容器备一份专属副本，是干净利落的做法。

### 5. 两种"没权限"：数字权限与 SELinux 标签

Linux 判断一个进程能不能读文件，要过**两道门**，上午和阶段五正好各栽了一道：

| | 第一道门：数字权限（DAC） | 第二道门：SELinux 标签（MAC） |
|---|---|---|
| 看什么 | `-rw-r-----` 这类 rwx 位、属主是谁 | 文件的标签（如 httpd_sys_content_t） |
| 查看 | `ls -l` | `ls -Z` |
| 栽过的案例 | **阶段十一这次**：副本是 640，容器里的 nginx 属于"其他人"，一格读权都没有 | **阶段五那次**：权限没毛病，但标签是 default_t，Nginx 进程不被允许读 |

记住这句口诀：**遇到 403，`ls -l` 和 `ls -Z` 都要看** — 只查一道门，另一道就会漏诊。

## 三、把上午的经历翻译成知识

### 事件 1：拉镜像被掐，换源解决

- `podman pull docker.io/...` 报 `connection reset by peer`：连接被中途掐断 — Docker Hub 在国内直连不通，是网络层的事，与命令、配置无关。
- 探活命令用 curl 敲四个国内镜像源的 `/v2/` 门：回 **401 的三家（DaoCloud、1ms、xuanyuan）是活的** — 401 的意思是"仓库在，请先表明身份"，这是注册服务器的正常应答；回 000 的 dockerproxy 才是真的连不上。
- 最终从 `docker.m.daocloud.io` 拉取成功。**结论**：在国内用容器，第一课就是镜像源；"连不上"先分清是对方不存在、还是路不通。

### 事件 2：容器版网站 403

- 现象：容器 Up、映射正常，curl 8080 返回 403，但落款是 `nginx/1.31.9` — 证明请求已经送到容器手里，纯粹是它读不到文件。
- `podman logs nginx-web` 给出实锤：`open() "/usr/share/nginx/html/index.html" failed (13: Permission denied)`。**容器排障第一动作永远是看 logs**，它相当于容器的 journalctl。
- `ls -lZ` 一锤定音：标签已是 container_file_t（`:Z` 生效，SELinux 清白），但数字权限是 `-rw-r-----`(640) — `cp` 把原文件的紧权限带过来了，容器里的 nginx 工人是"其他人"，被挡在门外。
- 修复：`chmod 644` 给副本放行（原文件在 /company 里继续锁着，不受影响）；因为是挂载，改完即刻生效，无需重启容器。

### 事件 3：端口发布僵死（上午的重头戏）

症状：127.0.0.1 访问 8080 正常、直连容器 IP 正常，但从外部（浏览器、宿主机对外 IP）访问 8080 全部挂起。排障链条一步步缩小范围，每一步都排除了一层：

1. 容器与映射在位（podman ps / podman port）→ 不是"没起来"
2. 停用 firewalld 对照，故障依旧 → 不是防火墙（nft 里也确实有 8080 的 accept 规则）
3. `ip_forward` 确认为 1 → 不是转发开关
4. `curl -v` 显示握手完成、请求发出、无人应答；`podman logs` 零新增记录 → 请求根本没到容器
5. `ss` 发现 8080 的监听者是 conmon；直连 `10.88.0.2:80` 秒出首页 → 容器和网桥无罪，故障锁定在"发布层"：conmon 托管的监听能接握手，却没把连接转交进容器（发布状态僵死）
6. 处置：**不修零件、换车厢** — stop、rm、按原命令重建容器，发布状态整套重铺，故障消失；浏览器验收通过

两个值得记住的点：
- **"本机 curl 自己的对外 IP"是条特殊路径（NAT 回流）**，它不通不代表外部用户不通；判断外部可达性，以真实外部客户端（浏览器）+ 服务端日志为准。
- **容器是易耗品**：状态僵死时，按原参数重建是标准处置，不是"没办法的办法" — 前提是数据放在挂载目录里，不随容器删除而丢失。这也是为什么部署时要把数据和容器分开。

### 命令地图（上午用过的全部命令，按用途归档）

| 命令 | 干什么的 | 你见过的关键输出 |
|---|---|---|
| `podman --version` | 看版本 | 3.4.4 |
| `podman images` | 本地镜像清单 | nginx 一行、167 MB |
| `podman pull 镜像全名` | 从仓库下载镜像 | 7 层 blob 逐层 done |
| `podman tag 旧名 新名` | 给镜像起别名 | 两行同 ID |
| `podman run -d --name 名 -p 宿:容 -v 宿:容 nginx:latest` | 按镜像起一个容器 | 返回容器 ID |
| `podman ps` / `podman ps -a` | 看运行中 / 全部容器 | Up / Exited (0) |
| `podman port 容器名` | 看映射关系 | 80/tcp -> 0.0.0.0:8080 |
| `podman logs 容器名` | 看容器日志（排障第一步） | 启动记录、403 实锤 |
| `podman exec 容器名 命令` | 钻进运行中的容器执行命令 | hostname -i → 10.88.0.2 |
| `podman stop / start 容器名` | 停 / 启容器（容器还在） | ps 与 ps -a 的区别 |
| `podman rm 容器名` | 删除容器（镜像与挂载文件不受影响） | 重建的前置步骤 |

## 四、五分钟只读复现（下次开机时跑一遍，对照预期自查）

```
podman images
podman ps -a
podman port nginx-web
podman exec nginx-web hostname -i
podman logs --tail 5 nginx-web
curl -sI http://127.0.0.1 | grep -i server
curl -sI http://127.0.0.1:8080 | grep -i server
curl -s http://10.88.0.2:80 | head -3
```
预期看到：
- 镜像表里 nginx 在列，167 MB；容器 nginx-web 为 Up（若停了，先 `podman start nginx-web`）
- 端口映射 `80/tcp -> 0.0.0.0:8080`；容器 IP 为 10.88.0.2
- 两个 Server 头一个是 **nginx/1.21.5**（宿主机版，80 端口），一个是 **nginx/1.31.9**（容器版，8080） — 这是区分"谁在伺候"的最快方法
- 直连容器 IP 能吐出首页的头几行（`<!DOCTYPE html>` 起头）

## 五、自测四问（先自己答，再看文末答案）

1. 把 nginx-web 用 `podman rm` 删掉、再按原命令 run 一个新的，网站首页文件会丢吗？为什么？
2. 在 Windows 浏览器输入 `http://192.168.6.135:8080` 后，请求依次经过哪些环节，才拿到首页？
3. 阶段五的 403 和阶段十一这次的 403，病因有什么不同？各该看哪个命令的输出来区分？
4. 拉镜像探活时，为什么回 401 的源反而是"活着"的好源？

---

### 答案

1. **不会丢**。首页文件本体在宿主机 /opt/webhtml，容器只是通过挂载借用；rm 删的是容器实例，不碰宿主机文件。这就是"数据与容器分离"的意义。
2. 宿主机网卡 ens33(192.168.6.135) → 防火墙放行 8080 → Podman 发布层（conmon 托管的监听）转交 → 容器网桥 cni-podman0 → 容器 10.88.0.2 的 80 端口 → 容器内 nginx 读取挂载进来的 index.html → 响应原路返回。
3. 阶段五是 **SELinux 标签**不对（文件标签 default_t，数字权限无问题），查 `ls -Z`；这次是**数字权限**不对（640 把"其他人"挡死，标签 container_file_t 正常），查 `ls -l`。遇到 403 两道门都要查。
4. 因为 /v2/ 是仓库的"大门"，正常工作的仓库会对未表明身份的访问回 401（需要认证） — 能回 401 说明服务器活着、路也通；回 000 或 connection reset 才是路根本不通。
